# Use context.AfterFunc for bound-holder cancel instead of one parked goroutine per Open

One goroutine parked per bound holder. Every successful Open spawns go t.watch(key, incarnation, ctx) (274:277:reclaim/table.go), which just blocks on <-ctx.Done() until cancellation. For Traefik's actual usage (one Open per plugin instance per dynamic-config reload) this is negligible, but it's a real, avoidable cost if a caller ever opens many keys per request instead of per plugin-instance lifetime.

Possible fix: for contexts where ctx.Done() != nil, Go 1.21+'s context.AfterFunc can register the cancel callback directly on context.WithCancel/WithTimeout contexts without spawning a goroutine at all (that's exactly what it was added for). go.mod already pins go 1.21, so the language feature is available. The catch: Yaegi v0.16.1's stdlib symbol table would need context.AfterFunc present, and the custom nil-Done() context (the Yaegi-shaped case tested by TestTable_HolderWithoutDoneChannelIsPolled, nilDoneCtx, 296:311:reclaim/table_test.go) can't use AfterFunc at all — <-nil never returns, so that path must keep the current goroutine+poll fallback. Net effect: worthwhile for the dominant real-world case, but needs a Yaegi-compatibility spike before adopting, and the code would need a ctx.Done() != nil branch instead of one uniform path. I'd call this "worth prototyping, not worth doing blind."
