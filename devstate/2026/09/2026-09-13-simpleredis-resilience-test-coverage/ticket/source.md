# SimpleRedis resilience probes as permanent tests

A bug hunt over `simpleredis` probed roughly a dozen suspected production killers (races, leaks, silent data corruption). Three were real and are being fixed in three SEPARATE PRs. Everything else came back HEALTHY. This PR locks in the probes that came back healthy as permanent regression tests, so nobody has to hunt them again, and lands the written record.

This is a COVERAGE + DOCS PR. Do NOT change any non-test file under `simpleredis/`. If a probe you write actually fails, do NOT fix the product here — report it on the delivery card and record it as a follow-up per `skill:opd-workflow:Issues` (debt file plus an `issues.md` row).

Reference material (already pushed): `git show origin/bugfixes20260913:simpleredis/BUGS.md`. The "Rejected (probed on this pass, not bugs)" table lists every healthy probe with its measurement. That table is the spec for this PR. The probe code itself was scratch and is NOT in the repo, so tests are written from the descriptions.

Probes to land as permanent tests (all currently PASS — invariant locks, not bug reproductions):

1. Chaos pool invariants. A `chaosFake` that, per command, randomly: replies honestly / delays 0-3ms / closes with no reply / replies `-LOADING Redis is loading the dataset in memory` / writes `$100\r\nshort` then closes. Drive it with ~24 goroutines for a bounded duration, each `Get` using a random context (Background, a short timeout, or one cancelled soon by `time.AfterFunc`). Keys k0..k63 where `GET kN` always answers `vN`. Assert: (a) no non-error `Get` ever returns another key's value; (b) at rest `len(inUseTurns) == cap(inUseTurns)` — no leaked turns; (c) `OverFrees() == 0`; (d) after quiescence, server-side open sockets <= PoolSize. Measured over 3 runs: ~12k connections churned, turns 4/4 every run, zero cross-talk. CRITICAL pitfall to encode as a CODE COMMENT so the next reader does not chase it: a sampler that reads `len(idleConns)` and then `len(inUseTurns)` is NOT a valid live-socket metric and will report up to 2x PoolSize. Two independent reasons: the two reads are not atomic, AND `release` publishes the socket into `idleConns` BEFORE calling `freeInUseTurn`, so a releasing socket is legitimately counted in both. Server-side PEAK open sockets also over-counts, because the server goroutine's exit lags the client's `Close` by a scheduling hop. Only settled / at-rest values are sound. Do NOT write an assertion on peak live sockets — it will flake.

2. RESP decoder fuzz. `FuzzReadReply` over `readReply`, asserting it never panics and never returns values together with a dirty (`clean == false`) stream. A panic here would be a PERMANENT pool turn leak, because `exec` releases without `defer` — that is why this target matters. Seed corpus via `f.Add`: `+OK`, `:12`, `-ERR bad`, `$-1`, `$0\r\n\r\n`, `$3\r\nabc`, `*2` with a bulk and a null, `*-1`, `*0`, `*1\r\n:9`, nested `*1\r\n*1\r\n:9`, `$9999999999999999999999`, `*99999999999999999999`, `$-`, `*-`, bare `$`, bare `*`, `\r\n`, `\n`, a bulk whose payload is longer than announced (`$2\r\nabcd`), `%2\r\n`, `>3\r\n`, `$18446744073709551616`, and `*1\r\n$18446744073709551616`. Add a `FuzzParseLen` asserting no `length+2` overflow. Measured clean at 7.04M execs over 91s, 51 corpus entries.

3. Lifecycle leak locks. (a) 200 `New` / use / `Close` cycles leave `runtime.NumGoroutine()` flat and server-side open sockets at 0. Measured: goroutines 3 -> 3, open 0, 800 accepts. (b) `Close` during in-flight commands ends with idle 0, server-side open sockets 0, and `len(inUseTurns) == cap(inUseTurns)`. Hold N Gets, `Close`, release the hold, wait, assert. The existing `holdGetsForTest` / `waitHeldGets` / `releaseHeldGetsForTest` helpers in `simpleredis/fake_redis_test.go` do the holding for you.

4. Yaegi error-path locks. Today `simpleredis/yaegi_test.go` covers ONLY happy paths (`RoundTrip`, `IncrAndEval`, `EvalNoScript`, `MSetEXNative`, `MSetEXLua`, `MatchSentinels`). Add interpreted coverage that these paths run cleanly (no interpreter panic, correct classification) when `simpleredis` is INTERPRETED: the dial-failure retry loop including backoff jitter, the I/O timeout mapping against a stalling peer, cancel-mid-command, pool wait, and truncated bulk. Reuse `writeGopathSimpleredis` and `writeGopathFile` from `yaegi_test.go`, and `startStallRedis` from `simpleredis/commands_deadline_test.go`. NOTE: another agent is concurrently fixing a real Yaegi sentinel-matching defect and is also adding Yaegi tests. Put YOUR Yaegi tests in a NEW file (for example `simpleredis/yaegi_errorpath_test.go`) and do NOT edit `simpleredis/yaegi_test.go`, so the two branches merge cleanly. Do not assert on `IsUnreachable` / `errors.Is` for AUTH or SELECT handshake failures — that is the other agent's bug and it is currently BROKEN interpreted; asserting it here would make your PR red.

5. Concurrent `MSetEX` unknown-command fallback. 16 goroutines x 25 `MSetEX` against a reject-MSETEX fake (`setRejectMSetEX` in `fake_redis_test.go`): 0 failures, `inUseTurns` full, `OverFrees() == 0`. Locks in that the `groupWrite` capability-cache race is benign.

6. No command injection. Keys, values, scripts, and TTLs are written as length-prefixed RESP bulk strings by `writeCommand`, so payload bytes are never scanned for CRLF. This was verified by INSPECTION only, not yet by a test — write the test. A key and a value each containing `\r\n` and a full inline `*1\r\n$4\r\nPING\r\n` payload must round-trip as DATA and must not be interpreted as a command by a fake that parses strict RESP.
